Fluxo de uma requisição SSR no Astro

O que acontece — passo a passo, do clique ao HTML renderizado — quando você abre o /painel do Zapt. Fundamentado nos arquivos reais do projeto.

Arquivos-base: astro.config.mjs · src/pages/painel.astro · src/lib/auth.ts · src/lib/api.ts
Visão geral

Os 3 atores dessa história

Antes do passo a passo, fixe os três participantes. Cada um roda num lugar diferente e "fala" com o outro por HTTP.

🌐

Navegador

O cliente. Faz o pedido HTTP e envia o cookie. Só recebe HTML+CSS. ( quase zero JS )

🟢

Servidor Astro (Node)

Roda o frontmatter das páginas a cada request. Tem acesso ao cookie e chama a API. É onde mora a SSR.

🟣

Backend .NET

A API REST em localhost:5104. Valida o cookie, devolve os dados em JSON. Não sabe que é Astro.

● Navegador ● Servidor Astro ● Backend .NET
O ciclo de vida

O pedido de /painel, passo a passo

Cada card mostra quem executa aquela etapa. Repare: a maior parte do trabalho acontece no servidor Astro (🟢), não no navegador.

1
🌐 Navegador

Usuário abre /painel

O browser dispara GET /painel e anexa o cookie HttpOnly de sessão que o login gravou. Esse cookie é a "identidade" dele.

↓
2
🟢 Servidor Astro

Adapter Node roteia para a página

O servidor Node (definido no astro.config.mjs) recebe a rota e executa src/pages/painel.astro. Começa pelo frontmatter (cercas ---). 

// astro.config.mjs — SSR ligado, roda como servidor Node
output: 'server',
adapter: node({ mode: 'standalone' }),
↓
3
🟢 Servidor Astro

Guarda de auth lê o cookie e valida

requireParent(Astro) extrai o cookie do header da requisição e repassa ao backend pra saber quem é. Se não for responsável → redireciona. O navegador nunca vê essa lógica. 

// src/lib/auth.ts
const cookie = Astro.request.headers.get('cookie') ?? '';
const user = await getCurrentUser(cookie);   // chama o .NET
if (user?.role !== 'Parent') throw Astro.redirect(...);
↓
4
🟢 Servidor Astro ↔ 🟣 Backend .NET

Busca os dados e monta o HTML

O frontmatter chama getChildren(cookie) (mais uma chamada ao .NET). Depois o template roda o .map() no servidor: os cards de criança já saem prontos como HTML. 

// src/pages/painel.astro — frontmatter (servidor)
children = await getChildren(cookie);

{/* template — também renderizado no servidor */}
{children.map((c) => (
  <article>...{c.name}... ⭐ {c.points}</article>
))}
↓
5
🌐 Navegador

Recebe HTML + CSS, sem React

What lands in the browser? HTML estático + CSS. Nada de runtime de framework. Por isso a página é leve e rápida — e por isso interatividade exige um <script> ou uma "ilha".

↓
6
🌐 Navegador

Clique = nova requisição (MPA)

Ao clicar "Nova Missão", o browser pede /cadastro-tarefas e todo o ciclo se repete. Não é SPA: cada navegação é uma ida-e-volta ao servidor que re-renderiza a página inteira.

Mecanismo #1

A anatomia de um .astro: dois andares

Toda a mágica da SSR vem do fato de um arquivo .astro ter duas regiões com tempos de execução diferentes. É o que distingue "código de servidor" de "código de navegador".

🟢 Frontmatter · roda NO SERVIDOR, a cada request 
---
const session = await requireParent(Astro);
const { user, cookie } = session;
children = await getChildren(cookie);   // chama o backend .NET
---

✅ Acesso ao Astro.request.headers (o cookie!), chamadas à API, banco, secrets. Nunca vai ao navegador.

🎨 Template · vira HTML que vai ao navegador 
<BaseLayout title="Painel">
  {children.map((c) => (
    <article>{c.name} · ⭐ {c.points}</article>
  ))}
</BaseLayout>

O .map() é avaliado no servidor. O browser recebe só o resultado (os <article> já desenhados).

💡 A regra de ouro

Tudo entre --- é servidor; tudo abaixo é o HTML que vira resposta. Confundir os dois é o erro nº 1 em Astro. "Por que o fetch do frontmatter envia meu cookie?" — porque ele roda no servidor, e o servidor não envia cookies do browser automaticamente. (Eis o mecanismo #2 ↓)

Mecanismo #2 · o ponto da sua trilha #6

Por que o SSR precisa repassar o cookie "na mão"?

No navegador, o fetch anexa o cookie sozinho. No servidor (frontmatter), não — o Node não sabe nada dos cookies do browser. Por isso o api.ts constrói o header Cookie manualmente. 

// src/lib/api.ts
const API_BASE = import.meta.env.SSR ? 'http://localhost:5104' : '';
//                  ↑ servidor: URL absoluta      ↑ cliente: caminho relativo (proxy do Vite)

await fetch(`${API_BASE}${path}`, {
  headers: {
    ...(cookie ? { Cookie: cookie } : {}),   // repasse manual da identidade
  },
  credentials: 'include',
});

🧪 Experimento da sua trilha (item #6)

Remova a linha ...(cookie ? { Cookie: cookie } : {}). Preveja o que acontece: a auth funciona no cliente (o browser manda o cookie sozinho), mas quebra no SSR (o servidor vira anônimo → 401 → redirect p/ login). É a prova viva de que frontmatter = servidor.

Consequência arquitetural

"Zero JS por padrão" — e o seu caso com o React

O Astro envia JavaScript ao navegador só onde você pede. Há dois caminhos pra dar interatividade, e o seu projeto usa um deles.

📜

Ilha de <script> ← seu projeto

Uma tag <script> com TS/JS vanilla, manipulando o DOM direto (getElementById, addEventListener). É o que o TaskForm.astro faz. Leve, mas sem estado reativo nem escopo de componente.

⚛️

Ilha de framework (client:)

Diretiva <Comp client:load /> hidrata um componente React/Vue/Svelte. Estado reativo, reuso. Você tem o @astrojs/react instalado… mas nenhuma página usa.

⚠️ Decisão pendente

Hoje você paga o custo (React nas dependências) sem o benefício (zero diretiva client:). É uma decisão de produto: continua no modelo script-vanilla (mais leve) ou adota ilhas React (mais estruturado)?
