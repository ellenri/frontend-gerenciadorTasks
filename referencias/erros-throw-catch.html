Erros, Throw e Catch em JS/TS

O mecanismo de exceções do JavaScript: o que é jogar um erro, como capturar, como ele sobe a pilha — e por que jogar um objeto que não é Error dá pau. Fundamentado no código real do Zapt.

Arquivos-base: src/lib/api.ts · src/lib/auth.ts · Core/Exceptions/DomainException.cs · astro/.../controller.js
1 · O sinal de emergência

throw — interrompe o fluxo normal

Quando algo dá errado (ou você quer parar tudo), você joga (throw) um valor. A execução para na hora nesse ponto e sobe procurando quem saiba lidar com isso (um catch). Se ninguém pegar, o programa "explode".

✅ Jogar um Error de verdade

No seu api.ts — o jeito certo:

throw new ApiError(message, response.status);
//  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
//  Um objeto Error (com message, name, stack).
//  As ferramentas conseguem "ler" ele.
O fluxo para aqui e sobe procurando um try/catch.

❌ Jogar um objeto comum

No seu auth.ts — o jeito que quebrou: 

throw Astro.redirect('/login');
//     ^^^^^^^^^^^^^^^^^^^^^^^^^^
//  Retorna um objeto Response (NÃO é Error).
//  As ferramentas não sabem ler → "Error: {}".
O fluxo para aqui também — mas vira erro de servidor (vimos o Error: {}).

⚡ O detalhe que poucos sabem

Em JavaScript você pode jogar qualquer coisa — string, número, objeto, Response. Mas não deveria. Jogue sempre Error (ou uma subclasse). Só assim você preserva o stack trace (a trilha de onde veio) e as ferramentas (devtools, Astro, Vite) conseguem te mostrar algo útil.

2 · Por dentro

Anatomia de um objeto Error

Um Error carrega informações pra depurar. É por isso que ele é o "tipo certo" a jogar — ele tem campos que um objeto qualquer não tem.

.message
O texto humano do erro. Ex.: "Erro 401 ao chamar /api/auth/me". Vem do super(message).
.name
O nome do tipo. Você pode sobrescrever: this.name = "ApiError". Ajuda a identificar de onde veio.
.stack
A trilha de chamadas (call stack). É o que aparece no terminal em vermelho. Só existe em Error de verdade.
.status (seu, custom)
Campos que VOCÊ adiciona numa subclasse. Seu ApiError soma status pra diferenciar 401 de 400.

🤔 Por que throw Astro.redirect() virou Error: {}?

Um Response não tem .message, nem .name, nem .stack. Quando o Astro tentou "embrulhar" ele num erro seguro, não achou nada pra mostrar → stringificou pra {}. Por isso a mensagem veio vazia. Lição: objeto que não é Error = informação perdida.

3 · Capturar

try / catch / finally — o apanhador

O try diz "vou tentar isso". Se um throw acontecer dentro dele, a execução pula pro catch (em vez de explodir). O finally roda sempre, erro ou não.

1 · try 
try {
  return await apiFetch('/api/auth/me', { cookie });
}
↓ se um throw acontecer aqui dentro
2 · catch (e) 
} catch (error) {
  // "error" é O QUE FOI JOGADO (pode ser qualquer coisa!)
  if (error instanceof ApiError && error.status === 401) return null;
  console.warn('[auth] API indisponível:', error);
  return null;
}
↓ roda sempre (opcional)
3 · finally 
// finally { ... }  // fecha arquivo, libera recurso, etc.

🔑 A peça-chave: instanceof

No catch você recebe o que foi jogado. Mas pode ser qualquer tipo de erro. O instanceof ApiError é como você pergunta: "esse erro é da minha classe?". Assim você decide o que fazer: 401 → "não logado", outro erro → "API caiu". Captura estreita e consciente, não "pega tudo e engole".

4 · Suas próprias exceções

Erros customizados: extends Error

Por que criar sua própria classe de erro? Pra carregar informação extra (um status) e pra distinguir tipos no catch com instanceof. É o mesmo padrão no frontend (TS) e no backend (C#).

// src/lib/api.ts — frontend (TypeScript)
export class ApiError extends Error {          // ← herda tudo de Error
  constructor(message, public readonly status) {
    super(message);                  // ← chama o construtor do Error (define message/stack)
    this.name = "ApiError";          // ← identifica a classe
  }
}
// No backend C# é a mesma ideia:  class DomainException : Exception { ... }

💡 O porquê de existir

Sem ApiError, um erro 401 e um erro 500 seriam "só erro" — você não saberia diferenciar. A subclasse etiqueta o erro com o contexto (status) que importa pra sua UI. O DomainException do backend faz o mesmo: etiqueta "essa quebra é uma regra de negócio" → o handler converte pra HTTP 400 limpo.

5 · O erro sobe

Propagação: o erro viaja pela pilha de chamadas

Se uma função joga um erro e não tem try/catch, o erro sobe pra quem chamou ela. E sobe, e sobe… até achar um catch. Se não achar ninguém → o programa para (ou o framework pega, como o Astro fez).

↑ erro sobe

↑ (mas aqui já foi pego)

// apiFetch joga:
throw new ApiError(message, response.status);   // status 401

// ...sobe até getCurrentUser, que tem o catch:
} catch (error) {
  if (error instanceof ApiError && error.status === 401) return null;  // ← capturado aqui
}

🔗 Onde isso explica o bug do seu auth.ts

O requireSession joga um Response (sem try/catch próprio). Esse erro sobe: requireParent → página → servidor Astro (runWithErrorHandling). O Astro é o "apanhador de último recurso" — ele pega QUALQUER coisa que chegue ao topo. Como era um Response (não Error), virou Error: {}. Ou seja: exceção não capturada = decisão de quem está no topo da pilha.

6 · Pra levar

Regras de ouro

✅

Jogue Error (ou subclasse)

Nunca string, número ou objeto comum. Preserva o stack e as ferramentas entendem.

⚠️

Não use throw pra fluxo normal

Tipo throw redirect() pra navegar. Exceção é pra casos excepcionais. (Seu auth.ts aprendeu isso.)

🎯

Capture estreito

Pegue só o que você sabe tratar. Use instanceof pra distinguir. Não engula erros silenciosamente.

🏷️

Crie subclasses com motivo

ApiError soma status; DomainException etiqueta "regra de negócio". Cada uma carrega o contexto que importa.

🕳️

Cuidado com catch vazio

catch (e) {} esconde bugs. No mínimo, logue (console.warn) como seu getCurrentUser faz.

📖

Leia o stack trace

As linhas at função (arquivo:linha) contam o caminho exato. É seu melhor amigo na depuração.
