Redirect em SSR: throw vs return

O problema real do seu auth.ts: o redirect precisa atravessar camadas de guardas até a página — mas um guarda que joga um Response vira Error: {}, e um guarda que retorna um Response quebra quem confia no tipo. Existe um terceiro caminho.

Arquivos-base: src/lib/auth.ts · src/pages/painel.astro · experimentos deste projeto
1 · O problema

O redirect precisa atravessar camadas

No frontmatter, só a página pode devolver um redirect de verdade (return Astro.redirect() — o retorno vira a resposta HTTP). Mas quem detecta o problema são os guardas, uma ou duas camadas abaixo. Como a decisão "vai pro login" sobe até a página?

📄 painel.astro (frontmatter)
única camada que pode return Astro.redirect() e isso virar resposta
↑chamou o guarda… e recebeu o quê?
🛡️ requireParent()
exige papel Parent · usa session.user.role
↑chamou o guarda… e recebeu o quê?
🛡️ requireSession()
exige login · detecta o problema primeiro

🧨 O dilema (você viveu os dois lados)

Se o guarda JOGA: throw Astro.redirect() → não é um Error → o servidor Astro vira Error: {} no dev (500). Além disso usa exceção pra fluxo normal — visitante sem login não é "erro", é terça-feira.

Se o guarda RETORNA o Response: return Astro.redirect() → o chamador recebe um Response onde esperava uma Session → session.user é undefined → undefined.role 💥 TypeError: Cannot read properties of undefined (reading 'role'). Você gerou esse erro no console!

2 · Os dois caminhos quebrados

Por que cada um falha (na prática)

❌ throw Astro.redirect()

o que existe hoje no seu auth.ts

if (!session)
  throw Astro.redirect('/login');
// o que o servidor vê:
Error: {}
  at createSafeError (...errors/utils.js:76:19)
  at recordServerError (...)
O Response sobe como exceção, ninguém o trata como redirect → vira erro 500. Dev tools mostram {}.

❌ return Astro.redirect()

a "correção inocente" — que você provou que quebra 

if (!session)
  return Astro.redirect('/login');
// o que o chamador sofre:
session.user        // → undefined
session.user.role   // → 💥 TypeError
O tipo de retorno vira uma mentira: às vezes Session, às vezes Response. Quem confia no contrato quebra.
3 · A sacada

Separe DETECTAR de DECIDIR

O guarda não precisa redirecionar — ele só precisa informar que não passou, com um valor honesto. Quem decide o que fazer (redirect, 404, o que for) é a página, porque só ela pode devolver a resposta.

🔴 Caminho atual: guarda decide (mal)

requireSessiondetecta E decide → joga Response
↓ Response sobe como exceção
requireParentnem roda direito (exceção passou por cima)
↓ continua subindo…
Servidor Astropega no topo → tenta virar erro → Error: {}
↓ o que o usuário recebe
tela de erro 500em vez de um redirect limpo

🟢 Caminho honesto: guarda informa, página decide

require* ou get*detecta → devolve null ("não deixei passar")
↓ valor honesto sobe normalmente
página (frontmatter)recebe null → SABE que não passou
↓ decide comautoridade
return Astro.redirect('/login')retorno da página = resposta HTTP de verdade ✅
↓ o que o usuário recebe
302 → /loginredirect limpo, sem exceção

💡 O padrão (forma geral)

// guarda: honesto — um único tipo de retorno
export async function requireParent(Astro): Promise<Session | null { ... }

// página: a única que pode responder
const session = await requireParent(Astro);
if (!session) return Astro.redirect('/login');   // ✅ retorno = resposta

É o mesmo espírito do null object pattern: getCurrentUser já faz isso no seu api.ts (devolve null em 401 em vez de jogar) — o auth.ts só não seguia o próprio padrão da casa.

4 · Trade-offs

Nenhum caminho é grátis — o que você ganha e paga

Abordagem Prós Contras Veredito
throw Response (atual) Uma linha por página; "mágica" de atravessar camadas Error: {} no dev; exceção pra fluxo normal; frágil entre versões do Astro evitar
return Response Não usa exceção Tipo de retorno mentiroso; TypeError no chamador (você provou!) nunca
return null + página decide Tipos honestos; página decide; redirect vira retorno real; consistente com getCurrentUser Duas linhas por página em vez de uma (o if (!session) return …) recomendado
middleware Astro Centraliza por rota (ex.: /painel/*); zero linhas por página Regra por padrão de URL (não por dado da sessão); mais uma peça pra entender futuro

🔍 Nota sobre o "atual"

Em produção, alguns runtimes do Astro acabam transformando um Response jogado em redirect de fato — comportamento que já foi documentado como padrão "arroz com feijão" em exemplos da comunidade. Mas não é garantido pelo contrato, e o dev server (como você viu ao vivo) reclama com Error: {}. Confiar em comportamento não-contratual é dívida: o caminho null + página decide funciona em qualquer runtime, dev ou prod.
