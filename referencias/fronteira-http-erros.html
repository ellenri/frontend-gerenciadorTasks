A fronteira HTTP: a exceção vira dado (e volta a virar exceção)

O erro nunca atravessa do backend pro frontend. Ele é traduzido na fronteira HTTP — vira status + JSON — e renasce como um erro novo no outro lado. Dois ciclos independentes, uma ponte de texto.

Arquivos-base: TaskItem.cs · DomainExceptionHandler.cs · src/lib/api.ts
1 · Quebrando o mito

Não existe "um compilador" — são dois programas

O frontend e o backend são processos separados, com linguagens, compiladores e runtimes diferentes. Eles não compartilham memória nem erros. A única ponte é HTTP.

Frontend (Astro) Backend (.NET)
Linguagem TypeScript C#
Compilador tsc · Vite · esbuild Roslyn (csc)
Runtime Node (SSR) + navegador .NET CLR
Processo Node na porta 4321 Kestrel na porta 5104
Erros Error / ApiError Exception / DomainException

🧠 A consequência crucial

Um compilador só enxerga o próprio lado. O tsc não sabe que o C# existe; o Roslyn não sabe que o TS existe. Portanto nenhum erro é compartilhado — cada erro "pertence" ao programa onde nasceu. O que viaja entre eles é só texto (requisição/resposta HTTP).

2 · O coração do conceito

A tradução na fronteira: exceção → dado → exceção

Uma exceção do backend é capturada e convertida em dados (status + JSON). Esses dados viajam pelo HTTP. No frontend, são lidos e viram uma exceção nova. Veja os dois ciclos e a tradução no meio:

💡 Repare: nunca foi o "mesmo" erro

O DomainException (C#) e o ApiError (JS) são objetos em runtimes diferentes. Um não "vira" o outro literalmente — um morre (no handler), sua mensagem viaja como texto, e um novo erro nasce do outro lado carregando aquele texto. A identidade se perde; só a informação atravessa.

3 · Passo a passo

Cenário real: criar missão sem título

A mesma mensagem ("O título da missão é obrigatório.") viaja pelos dois mundos. Veja o código exato em cada etapa. 

// 🟣 BACKEND — Core/Entities/TaskItem.cs
if (string.IsNullOrWhiteSpace(title))
    throw new DomainException("O título da missão é obrigatório.");   // ← nasce aqui (C#)
// 🟣 BACKEND — ExceptionHandling/DomainExceptionHandler.cs  (o tradutor)
if (exception is not DomainException) return false;   // só trata a dele
httpContext.Response.StatusCode = 400;                        // ← vira STATUS
await httpContext.Response.WriteAsJsonAsync(new ProblemDetails {
    Title = "Regra de negócio",
    Detail = domainException.Message                      // ← vira JSON no corpo
});
────────────────── pelo fio HTTP:  400  { "title":"Regra de negócio", "detail":"O título..." }  ──────────────────
// 🌐 FRONTEND — src/lib/api.ts  (apiFetch relê e rejoga)
if (!response.ok) {
  const body = await response.json();
  if (body?.detail) message = body.detail;                 // "O título da missão..."
  throw new ApiError(message, response.status);        // ← renasce aqui (JS, status 400)
}
// 🌐 FRONTEND — TaskForm.astro  (catch mostra na tela)
} catch (error) {
  const message = error instanceof ApiError ? error.message : "Tente novamente.";
  showFeedback('error', message);                       // ← usuário vê a mensagem
}
4 · A pergunta original

"Como o compilador sabe se é erro de frontend ou backend?"

Não sabe. E não precisa. O frontend não recebe "um erro do backend" — recebe um número (status HTTP) e um JSON. É a convenção do status que dá a pista do que aconteceu.

Status Significado (convenção HTTP) Quem "causou"
2xx Sucesso — deu tudo certo —
400 Requisição inválida (regra de negócio quebrada) você mandou algo errado
401 Não autenticado (sem cookie / cookie inválido) você não está logado
403 Sem permissão (role não permite) você é criança, não responsável
404 Não encontrado o recurso não existe
5xx Erro interno do servidor o backend quebrou por dentro

🔎 Então, no frontend, como DISTINGO os erros?

Não é o compilador — é o tipo do erro. Se veio da API, é ApiError (tem .status); se é bug do próprio frontend, é um erro nativo (TypeError etc.). O instanceof ApiError é o detector. Igualzinho à seção 3 do HTML "erros-throw-catch".

5 · No frontend, dois "sabores" de erro

Erros da API × erros do próprio frontend

No catch do frontend, o que chegou pode ter duas origens. Saber diferenciar é o que te permite agir certo.

🌐 ApiError — veio da API

O backend respondeu com status de erro. Tem .status (400, 401…). Você mostra a mensagem pro usuário ou redireciona pro login. 

if (error instanceof ApiError && error.status === 401)
  return null;
src: api.ts · getCurrentUser

💥 TypeError etc. — bug do frontend

Seu próprio JS quebrou (ex.: undefined.role). Não tem status. É pra consertar o código, não pra mostrar pro usuário. 

// veio do SEU código, não da API
console.warn('bug inesperado:', error);
src: api.ts · getCurrentUser (o "else")

✅ Regra prática

No catch, pergunte sempre: "esse erro veio da API ou do meu código?". Use instanceof ApiError pra separar. Erro da API → trate pra UX (mensagem/login). Erro nativo → investigue e corrija. Nunca engula silenciosamente.
