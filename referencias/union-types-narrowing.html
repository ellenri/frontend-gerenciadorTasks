Union Types & Narrowing

Quando uma variável pode ser uma coisa ou outra (Session | string), o TypeScript não deixa você usar até conferir — e, conferindo, ele estreita o tipo naquele trecho. O mecanismo que você usou no refactor do auth.ts.

Arquivos-base: src/lib/auth.ts · src/lib/api.ts · src/pages/painel.astro
1 · O union type

"Uma coisa OU outra" — a caixa com dois conteúdos

Depois do refactor, os guardas do seu auth.ts devolvem Promise<Session | string>. A barra vertical (|) lê-se "ou": a promessa pode se realizar como uma sessão (passou) ou uma string (URL pra onde ir).

📦

Session | string

Caixa fechada: pode conter duas coisas. O TS não deixa usar até abrir.

🔑

Session

{ user, cookie } — usuário autenticado e o cookie pra repassar.

🔗

string

'/login' ou '/crianca' — uma URL. A decisão de redirect. 

// src/lib/auth.ts — o contrato do refactor
export async function requireParent(Astro): Promise<Session | string> {
  const session = await getSession(Astro);
  if (!session) return '/login';                          // → string
  if (session.user.role !== 'Parent')
    return homeForRole(session.user.role);              // → string
  return session;                                            // → Session
}

💡 Por que isso é honesto?

Compare com os caminhos quebrados: throw Response escondia a informação numa exceção; return Response mentia o tipo. O union declara as duas verdades de forma explícita — o compilador passa a exigir que TODO consumidor trate os dois casos. Nada escapa.

2 · O estreitamento

Narrowing: conferir para confiar

Narrowing = o compilador analisa o fluxo do código e descarta possibilidades do union conforme as checagens que você faz. A mesma variável tem tipos diferentes em trechos diferentes — ditados pelo caminho que a execução pode tomar.

session: Session | string
duas possibilidades
↓pergunta: typeof session === 'string'?
✓ sim — dentro do if
session: string
(estreitou p/ URL)
✗ não — depois do if
session: Session
(descartou string)
// src/pages/painel.astro — a linha que TODO frontmatter ganhou
const session = await requireParent(Astro);
if (typeof session === 'string') return Astro.redirect(session);
//                                        └─ só aceita URL: como session aqui É string, passa ✅

const { user, cookie } = session;   // ✅ sem erro — aqui session JÁ é Session

🚫 E sem o if?

session.user;
Error: Property 'user' does not exist on type 'Session | string'.

Foi exatamente o erro que apareceu no seu editor no meio do refactor — o compilador te obrigando a abrir a caixa antes de usar. No runtime, o equivalente seria o TypeError: Cannot read properties of undefined (reading 'role') que você gerou no console: mesmo bug, mas o narrowing o pega na escrita, não em produção.

3 · O arsenal

As formas de estreitar (todas já no seu projeto)

Narrowing não é só typeof — qualquer checagem que o compilador consiga raciocinar serve. Você já usa quatro delas sem saber o nome:

Guarda O que faz Onde você usa
typeof separa primitivos (string | number...) auth.ts / 15 páginas — typeof session === 'string'
instanceof identifica a classe de um objeto api.ts — error instanceof ApiError (aí .status existe)
truthiness (!x) tira null/undefined do union api.ts — return user ? { user, cookie } : null
igualdade literal estreita uniões de literais auth.ts — role !== 'Parent'; e o TS sabe que sobrou 'Child'…
'prop' in obj "tem essa propriedade?" (ainda não — útil pra objetos de formatos diferentes)

🔎 Curiosidade do seu próprio código

No catch do getCurrentUser, o error chega como unknown (o TS não adivinha o que foi jogado). O instanceof ApiError estreita de unknown pra ApiError — e só por isso o error.status compila. É o mesmo mecanismo do typeof, só que para classes.

4 · A pegadinha

Onde o narrowing NÃO alcança

O estreitamento vale para o fluxo linear do código. Ele se perde quando uma função roda "mais tarde" (callback), quando a variável é reassinalada, ou quando o TS não consegue provar o estado naquele ponto:

🔴 Callback: a garantia expira

let session = await requireParent(Astro);
if (typeof session === 'string') { ... }

setTimeout(() => {
  session.user  // 🔴 erro! aqui volta a ser
}, 100);            //    Session | string

O callback roda no futuro; entre o if e ele, outra parte do código pode ter trocado session. O TS não consegue garantir — e recusa. A checagem teria que estar DENTRO do callback.

🔴 Reassinalação: o tipo volta

let session = await requireParent(Astro);
if (typeof session === 'string') { ... }

session = '/qualquer-coisa';  // reatribuiu!
session.user;                  // 🔴 Session | string

O estreitamento é um estado de conhecimento do compilador naquele ponto do fluxo. Qualquer reatribuição "reseta" o conhecimento pro tipo declarado.

🧭 Moral da pegadinha

Narrowing não é uma etiqueta permanente na variável — é o que o compilador sabe no trecho, dado o caminho que o código pode ter percorrido até ali. Callbacks e reatribuições quebram a garantia. Por isso o padrão idiomático é estreitar e usar imediatamente (ou extrair pra uma const com o tipo já garantido).

5 · Recap

O refactor inteiro, visto por essa lente

Releia o que você implementou hoje com o vocabulário novo: 

// 1. O guarda declara as DUAS verdades (union honesto):
export async function requireParent(Astro): Promise<Session | string>

// 2. A página CONFERENCE (guarda de tipo) e estreita:
if (typeof session === 'string')
  return Astro.redirect(session);   // trecho onde session é string

// 3. Depois do if, session é Session — e o restante da página
//    usa user/cookie SEM precisar conferir de novo:
const { user, cookie } = session;      // trecho onde session é Session

📝 As três frases pra lembrar

1. Union type = caixa com conteúdos possíveis; o TS exige que você abra antes de usar.

2. Narrowing = o que o compilador sabe num trecho, dado o fluxo — typeof/instanceof/truthiness estreiam.

3. O estreitamento é local e temporário: callbacks e reatribuições resetam. Estreite e use.
